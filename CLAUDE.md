# Media Tools (repositório `conversor-midia`)

Plataforma web **gratuita** para converter, comprimir e editar imagens e vídeos **direto no navegador**. Sem conta, sem login, sem backend: o visitante escolhe um arquivo, escolhe o que fazer e baixa o resultado. Interface em **português do Brasil**.

Este arquivo é a fonte das regras do projeto. Os **métodos** de trabalho (checklists, procedimentos) estão nas Skills de `.claude/skills/` e **não são repetidos aqui**.

## Funcionalidades
- **Imagens (primeira versão)**: converter JPG/JPEG, PNG e WEBP para JPG, PNG, WEBP, BMP, TIFF, ICO e PDF; comprimir; redimensionar; recortar, girar e espelhar; processar vários arquivos; baixar os resultados; criar colagem de 2 a 9 fotos (grade ou livre), em JPG.
- **Vídeos**: prontos: editar (barra do vídeo com miniaturas: dividir, excluir pedaços, ajustar as pontas, desfazer, com o resultado no player na hora; textos com 12 estilos, desenhados nos quadros ao salvar; filtros, ajustes de cor e velocidade do vídeo inteiro), recortar o quadro (proporções Livre, 1:1, 4:5, 9:16, 16:9 e 3:2) e comprimir (três níveis ou "até X MB" para WhatsApp, e-mail e Discord, com tamanho estimado antes), com entrada MP4, MOV e WEBM de até 1 GB e saída no mesmo formato; extrair o som em M4A, WEBM (copiado sem refazer quando o som cabe no formato) ou MP3; diminuir a resolução (1080p, 720p, 480p ou 360p; aumentar não é oferecido); converter entre MP4, MOV e WEBM (copiando o que o formato novo comporta); criar GIF animado de um trecho de até 15 segundos (o GIF fica com os vídeos, não com as imagens).
- Fora de escopo agora: autenticação, banco de dados, backend, SVG como entrada, HEIC, qualquer formato fora da lista acima (entrada só JPG, PNG e WEBP; vídeo só MP4, MOV e WEBM). Só entram mediante pedido explícito. AVIF, HEIC e JPEG XL como saída exigem codificador em WebAssembly (dependência pesada; HEIC também tem questão de patentes): decidir quando pedidos.

## Tecnologias
React 19 · TypeScript 7 (estrito) · Vite 8 · Tailwind CSS 4 · React Router 8 (aplicação de página única) · lucide-react · fonte hospedada no site, só o subconjunto latino: Inter (`@fontsource-variable/inter`), declarada em `src/styles/fonts.css` · Canvas API (`OffscreenCanvas` e `createImageBitmap` onde houver suporte) · codificadores próprios de PNG, BMP, TIFF, ICO, PDF e GIF animado em TypeScript (`core/image/encode`, sem dependência; o PNG comprime pelo `CompressionStream` do navegador) · Web Workers · fflate (ZIP do download em lote, carregado sob demanda dentro do Worker) · react-image-crop (área de recorte na tela, só nas páginas de recortar) · Mediabunny (vídeo via WebCodecs, dentro do Worker de vídeo, só nas páginas de vídeo) · @mediabunny/mp3-encoder (LAME em WebAssembly, para o MP3 do Extrair áudio, carregado sob demanda dentro do Worker de vídeo) · Vitest 5 (Node + modo navegador com Playwright) · Playwright · oxlint · GitHub · Vercel (hospedagem estática). FFmpeg.wasm não é usado (ver Vídeo).

Navegadores suportados (piso herdado do Tailwind 4): Safari/iOS 16.4+, Chrome/Edge 111+, Firefox 128+.

## Comandos
`package.json` é a fonte; não invente scripts. Ambiente: Node 24+, npm, Windows.
- `npm run dev`: servidor de desenvolvimento. A vitrine de tokens e componentes fica em `/_design` (publicada, fora da navegação, sem indexação).
- `npm run build` / `npm run preview`: build de produção e prévia local.
- `npm run typecheck` · `npm run lint` (oxlint, avisos reprovam).
- `npm test`: Vitest, projetos `unit` (Node, `*.test.ts`) e `browser` (Chromium real, `*.test.tsx`).
- `npm run test:e2e`: Playwright no build de produção (Chromium em 360, 768 e 1280 px; as ferramentas de imagem e de vídeo também no Firefox e no WebKit), inclusive a vitrine (`/_design`). O `preview` aplica os cabeçalhos do `vercel.json`, então a CSP é testada localmente.
- `npm run icons`: regenera favicon e ícones do PWA a partir da geometria do logotipo.
- `npm run fixtures`: regenera as imagens e os vídeos de teste em `tests/fixtures/` (os vídeos são codificados pelo Mediabunny no Chromium do Playwright).
- Primeira vez: `npx playwright install chromium firefox webkit`.

## Arquitetura
- Camadas: UI (React) → hooks/estado → cliente do Worker → Worker → núcleo puro (`core/`, sem DOM nem React). Dependências só apontam para baixo.
- Lógica de processamento em funções puras e testáveis; componentes só apresentam e orquestram.
- **Todo processamento de pixels (decodificar, redimensionar, codificar) roda em Web Worker**, com detecção de recurso e fallback; a thread principal só cuida da interface. É decisão arquitetural fixa, não otimização opcional.
- Operação de processamento = função com entrada tipada → `Promise<Blob>`, com `AbortSignal` e progresso. Protocolo do Worker tipado; todo pedido recebe resposta de sucesso ou erro.
- Lote com concorrência limitada; erro de um arquivo não derruba os demais.
- Componentes pequenos, uma responsabilidade; extrair duplicação real (regra de negócio repetida), não semelhança visual.
- Ferramenta nova = módulo novo, sem alterar as existentes. Sem abstração antes de haver 2–3 casos reais.
- **Mudança arquitetural grande** (estrutura de pastas, nova camada, mudança de protocolo, nova dependência estrutural): explicar motivo, alternativas e impacto e **esperar aprovação** antes. Skill: `architecture-review`.

## Padrões de código
- TypeScript estrito (`strict`); sem `any` sem justificativa em comentário; tipos explícitos nas fronteiras (Worker, `core/`).
- Funções curtas, nomes descritivos, early return, sem código morto nem comentário que repete o código; comente o **porquê** de decisões não óbvias.
- Idioma: conversar e documentar em **português do Brasil**; identificadores de código em **inglês**; textos da interface seguem o idioma definido para o produto.
- Estilos com Tailwind utilitário; cores, fontes e espaçamentos via **tokens do tema**, nunca valores soltos espalhados.
- Erros: nunca engolir (`catch` vazio); mensagens ao usuário em linguagem simples, detalhes técnicos só no console de desenvolvimento.
- Recursos liberados sempre: `URL.revokeObjectURL`, `ImageBitmap.close()`, `Worker.terminate()`, limpeza em `useEffect`.
- Lint: oxlint (padrão do template do Vite), com avisos reprovando; sem avisos ignorados.

## Processamento local de arquivos
- **Padrão: o arquivo nunca sai do dispositivo.** Nenhum `fetch`, XHR, `sendBeacon` ou WebSocket com conteúdo de arquivo. Enviar a servidor exige necessidade comprovada **e autorização explícita do usuário**.
- Arquivo do visitante é **dado não confiável**. Valide por assinatura de bytes e por decodificação real, não por extensão ou `file.type`.
- Limites antes de decodificar: bytes, número de arquivos e dimensões (memória decodificada ≈ largura × altura × 4).
- Recodificar via canvas remove metadados (EXIF/GPS); PNG/WEBP com transparência → JPEG exige cor de fundo definida; confirme na saída que o formato pedido foi realmente gerado (alguns navegadores trocam para PNG em silêncio).
- **O resultado não fica mais pesado sem motivo** (auditoria de 21/11/2026, com fotos e vídeos parecidos com os reais). Foto JPG gravada de novo em formato com perdas (JPG, WEBP, PDF: girar, redimensionar, recortar, converter) nunca usa qualidade acima da original, estimada pela tabela de quantização do cabeçalho (`core/image/jpeg-quality.ts`): uma foto do WhatsApp (cerca de 75) regravada a 92 crescia 33%. PNG sai pelo codificador próprio (`core/image/encode/png.ts`), porque o dos navegadores grava sempre RGBA e comprime pouco: paleta quando há até 256 cores, RGB quando é opaca, RGBA nos demais casos, filtro por linha, deflate do `CompressionStream` (um print de tela caiu de 183 KB para 7 KB; uma foto de 12 MP, de 24,7 MB para 15,3 MB, em cerca de 4 s em vez de 1 s). Dentro do ICO, sempre RGBA (o que o Windows garante ler). BMP e TIFF ficam sem compressão, pela compatibilidade.
- Medidas para decidir (tamanho final, recorte): as de `item.image` depois da prévia, que são as da imagem decodificada e já orientada, como o Worker a verá. O cabeçalho de PNG e WEBP não informa a orientação.
- Girar e espelhar: as 8 orientações vêm de `core/image/orientation.ts`, que dá as medidas, a matriz do canvas (só 0, 1 e −1: sem reamostrar) e o CSS da prévia. A prévia e o arquivo usam a mesma conta, conferida em teste.
- Colagem: `core/image/collage.ts` dá o plano (medidas do arquivo e, para cada foto, onde entra, giro, cantos, moldura e que parte dela aparece), e a prévia e a tarefa `collage` do Worker de imagens usam o mesmo plano. O Worker decodifica uma foto por vez (9 fotos de 12 MP juntas passariam de 400 MB), separa a parte que aparece, reduz por `drawResized` e desenha. O arquivo sai em JPG, com o maior lado em que a foto mais detalhada aparece sem ampliar, entre 1080 e 2048 px, e qualidade 0,9 limitada à da foto JPG mais caprichada. A ordem inicial é a da escolha dos arquivos (as fotos ficam prontas uma de cada vez); no estilo livre, as fotos se espalham de novo a cada chegada até a pessoa mexer em uma.
- Recortar: a área é guardada em pixels inteiros da imagem orientada (`core/image/crop.ts`); a tela a desenha em porcentagem sobre a prévia reduzida. O Worker copia exatamente a área e recusa área fora da imagem.
- Reduzir imagem no Worker: sempre por `drawResized` (em `image.worker.ts`), inclusive prévias e ICO. Num passo só, o Firefox, que não tem `imageSmoothingQuality`, cria listras falsas (moiré). Uma sonda decide: onde um passo só sai bom (Chromium), um passo; senão, etapas de metade. Testes E2E de moiré no Chromium e no Firefox.
- Vídeo: a primeira barreira é `core/video/inspect.ts` (tamanho e assinatura de bytes); a abertura real (faixas, duração, codecs, o que o navegador decodifica e codifica) é no Worker. Medidas do vídeo = pixels quadrados com a rotação aplicada, o mesmo espaço em que o Mediabunny recorta. O resultado sai sem metadados (`tags: {}`: localização, data, aparelho), conferido em teste; faixa descartada pelo Mediabunny vira erro, nunca vídeo mudo em silêncio.
- Ver como ficou: o resultado ganha uma URL temporária ao terminar (`useImageBatch`, `useVideoTool`), liberada quando o resultado é descartado (opções mudadas, arquivo removido ou trocado, saída da tela).
- Não persistir arquivos do usuário (localStorage, IndexedDB, cache) sem decisão explícita.
- Skills: `security-auditor` (segurança), `performance-optimization` (memória).

## Segurança
- Proibido sem exceção justificada: `dangerouslySetInnerHTML`, `innerHTML`, `eval`, `new Function`, `document.write`.
- Nome de arquivo, mensagens e metadados são texto não confiável: nunca como HTML.
- Sem segredos no cliente (tudo no bundle é público; inclui `VITE_*`). Não registrar informação sensível em logs.
- Hospedagem com cabeçalhos de segurança (CSP restritiva, `nosniff`, `Referrer-Policy`, `Permissions-Policy`) em `vercel.json`, conferidos por `tests/e2e/security.spec.ts`. COOP/COEP só se o FFmpeg multi-thread for adotado. `media-src 'self' blob:` (aprovado em 19/11/2026) permite ao player mostrar o vídeo escolhido pela URL temporária; nada de fora do site. `script-src 'self' 'wasm-unsafe-eval'` e `worker-src 'self' blob:` (aprovados em 21/11/2026) existem só para o codificador de MP3: ele roda em WebAssembly num Worker que o próprio pacote cria a partir de `blob:`. `'wasm-unsafe-eval'` libera compilar WebAssembly, não `eval` de JavaScript; o teste confere as diretivas exatas e a ausência de `'unsafe-eval'` e `'unsafe-inline'`.
- A CSP não permite `data:`: o build não embute `.woff2` (`assetsInlineLimit` em `vite.config.ts`). Recurso novo (fonte, Worker, imagem) precisa caber na CSP ou ela deve ser ajustada conscientemente.
- Nenhuma afirmação de "aplicação segura": relate escopo e limites da verificação.

## Desempenho
- Medir antes de otimizar; não fazer otimização prematura (a regra do Worker acima não é otimização prematura).
- Bundle inicial enxuto; bibliotecas pesadas via `import()` sob demanda.
- Considerar celulares e computadores modestos: concorrência baixa, limites de tamanho, mensagens claras quando faltar memória.
- Liberar memória por arquivo processado; não manter Blobs/bitmaps grandes em estado reativo do React.

## Estratégia de testes
- **Vitest**: lógica pura (assinaturas de bytes, dimensões, nomes de saída, filas, mapeamento de erros, codificadores) no projeto `unit`; componentes e qualquer coisa que dependa de Canvas no projeto `browser` (Chromium real). jsdom não é usado: **não** validar conversão com mock.
- Formatos escritos pelo app são conferidos por leitores independentes (`src/test/format-readers.ts`) e, onde o navegador lê o formato (BMP, ICO), também pela decodificação dele.
- **Playwright**: fluxo real (selecionar → processar → baixar → conferir o arquivo). Verificar formato real (assinatura), dimensões e pixels da saída, não só "baixou".
- Casos obrigatórios: conversões entre formatos, arquivo inválido/corrompido/vazio, arquivo grande, erro no processamento, múltiplos arquivos.
- O WebKit do Playwright no Windows não tem `OffscreenCanvas` nem decodificador de vídeo (`VideoDecoder`): lá os testes de conversão e de recodificar vídeo se pulam sozinhos e só a mensagem de navegador incompatível (e o corte rápido, que só copia) é conferida. O Safari real tem os recursos e precisa de teste em macOS ou iOS. Em 21/11/2026 uma política de Controle de Aplicativo do Windows passou a bloquear o executável do WebKit do Playwright neste computador, e em 24/11/2026 também o do Firefox (`spawn UNKNOWN` ao abrir); em 27/11/2026 os dois voltaram a abrir. Se o bloqueio voltar, não contornar; relatar o que ficou sem teste. No Firefox, sem AAC, os testes de salvar vários pedaços e de mudar a velocidade conferem a explicação e o botão desligado em vez do arquivo.
- Vídeo: os vídeos de teste são lidos por um leitor independente do Worker (`src/test/video-reader.ts` no navegador; Mediabunny só para ler, sem decodificar, no E2E), e as cores dos quadros são conferidas pelo canal dominante (codificar altera os valores, e cada navegador converte cores do seu jeito). O som extraído é conferido por `src/test/audio-reader.ts`: pacotes iguais aos do original na cópia e, no refeito, o tom de 440 Hz dos vídeos de teste (cruzamentos do zero) e o volume.
- O `@mediabunny/mp3-encoder` só é importado dentro do Worker: está em `optimizeDeps.include` do projeto `browser` do Vitest, senão o Vite o descobre no meio dos testes e recarrega a página.
- **Funcionalidade só está concluída com testes adequados passando** (unit + E2E relevantes), typecheck e lint limpos. Interface funcionando não basta. Relatar o que não foi testado. Skill: `test-driven-development`.

Fica só no Worker de vídeo (510 KB, cerca de 125 KB comprimidos, com o gravador de MP3), carregado só nas páginas de vídeo. FFmpeg.wasm foi descartado (GPL, cerca de 31 MB, parado desde 04/2025); fica como alternativa futura só para formatos exóticos.

## Vídeo
- Feature isolada (`features/video-tools`), Worker próprio (`workers/video.worker.ts`, com o Mediabunny), carregado sob demanda só nas páginas de vídeo.
- Limites: arquivo e resultado ficam na memória (`BufferTarget`): 1 GB por vídeo, avisado antes de escolher; progresso real e cancelamento (encerra o Worker) sempre. Falta de memória vira mensagem própria.
- Preferir não recodificar. Corte de um trecho (tarefa `trim`): **Exato** copia o vídeo quando o início cai num quadro-chave (ou no começo) e recodifica quando não cai (não há "corte inteligente" que recodifique só o começo); **Rápido** sempre copia, a partir do quadro-chave anterior, que fica escondido antes do zero (MP4 e MOV). WEBM não guarda quadros antes do zero: lá só existe o Exato, e o som pode ser recodificado em Opus. O Editar vídeo usa só o Exato (o que a pessoa vê é o que sai; decisão do usuário em 24/11/2026); o Rápido continua no Worker.
- Editar vídeo (`features/video-tools/edit`, `core/video/timeline.ts`), que substituiu o Cortar trecho a pedido do usuário (24/11/2026, inspirado no layout de editores de celular): player sem controles do navegador, que toca o vídeo editado pulando os pedaços excluídos (sem processar nada até salvar); botões Tocar, Dividir, Excluir, Desfazer, Refazer e zoom; embaixo, a barra do vídeo editado sob uma linha fixa no meio, que rola (dedo, mouse, roda ou setas: 0,1 s, com Shift 1 s) e mostra miniaturas. As miniaturas vêm da tarefa `thumbnails` do Worker (até 120 quadros pequenos lado a lado num JPG, uma URL temporária; só as visíveis são desenhadas, como fundo de cada quadrinho). Pedaço é botão: tocar nele marca o pedaço inteiro; as alças nas pontas da marca (controles deslizantes: arrastar ou setas) a encolhem até cobrir só o que deve sair, e "Excluir" tira essa parte: o pedaço perde uma ponta, vira dois ou some, sem precisar dividir (pedido do usuário em 24/11/2026, depois de não entender o "Dividir"). Marcar não muda o vídeo; o player mostra o quadro da alça movida; tirar o vídeo inteiro não pode. O ajuste fino (campos de tempo) e o aviso de metadados saíram do painel a pedido (26/11/2026): a marca é feita só pelas alças. Desfazer guarda até 100 passos. Salvar: pedaços encostados viram um; um trecho só é um corte Exato (copia quando dá); vários, a tarefa `join`. A barra tem `contain: inline-size`: sem isso, medir a barra e alargar o conteúdo se alimentavam sem fim. Rolagem logo depois de tocar num pedaço (o navegador mostrando o botão focado) não move a linha.
- Comprimir: o vídeo é refeito numa taxa de bits calculada pela área do quadro e pelo nível (`core/video/compress.ts`; Média limita o lado menor a 1080, Forte a 720), e o som é copiado. A tela mostra resolução final e tamanho estimado antes, e avisa quando o nível quase não reduz. Se o resultado não ficar menor, entrega-se o original intacto (com os metadados), como no Comprimir imagem. Ao abrir o vídeo, o Worker confere se o codificador respeita a taxa (dois clipes de teste minúsculos, em taxa baixa e alta): o H.264 do Firefox do Playwright ignora a taxa, e lá a tela explica que comprimir não funcionaria em vez de prometer um tamanho. **Até X MB** (destinos em `app/destinations.ts`, limites conferidos em 25/11/2026: WhatsApp 64 MB em 720p, e-mail 20 MB, Discord 20 MB): `planForTarget` dá a taxa do vídeo = (alvo × 8 ÷ duração) − som, com 5% de folga, e a maior resolução (até a do destino) cuja taxa mínima cabe; nunca acima da do original. Vídeo longo demais para o limite: a tela avisa e o botão fica indisponível. O atalho do WhatsApp abre com `?destino=whatsapp`.
- Juntar pedaços (Editar vídeo com mais de um pedaço, tarefa `join`): uma conversão do Mediabunny com `process` nos quadros e no som (`core/video/remove.ts` dá os pedaços e quanto cada um anda para encostar no anterior). Quadro em parte removida sai; o som é cortado na amostra exata, então a emenda fica contínua e junto da imagem. Vídeo e som são sempre refeitos: o som sai em AAC no MP4 e no MOV (o Firefox não gera AAC: lá salvar vários pedaços fica indisponível com explicação) e em Opus no WEBM. Sobrando um pedaço só, vira um corte comum (que pode copiar).
- Mudar resolução (`core/video/resize.ts`): só **diminui** (1080p, 720p, 480p, 360p pelo lado menor; iguais ou maiores que a do vídeo ficam desligadas, com a explicação de que aumentar não melhora a qualidade, e o Worker recusa medidas maiores). Usa a mesma tarefa do Comprimir (`compress`: medidas e taxa, som copiado), sem prometer tamanho, então funciona também no Firefox. A taxa é de qualidade alta, mas nunca acima da do original proporcional à área (senão um vídeo já comprimido, como o do WhatsApp, cresceria). A escolha vale para os próximos vídeos enquanto for menor que a deles.
- Extrair áudio (`core/video/audio.ts`): o som é **copiado** quando cabe num arquivo de som comum (AAC em M4A; Opus e Vorbis em WEBM, não em Ogg, que o Safari só passou a tocar bem depois) e refeito a 192 kbit/s nos demais casos: M4A em AAC (o Firefox não gera AAC: indisponível com explicação) e MP3 pelo LAME (lento: cerca de 18 vezes o tempo real no computador). A cópia usa `copy: { mode: 'forced' }`: sem isso o Mediabunny refaria em silêncio o Opus, que começa alguns milissegundos antes do zero; o teste confere pacotes iguais aos do original. Os formatos indisponíveis aparecem desligados, com o motivo; o escolhido vale para os próximos vídeos enquanto existir para eles. Sem metadados (conferido também no MP3).
- Converter vídeo (`core/video/convert.ts`): oferece os dois formatos diferentes do original. O que o formato novo comporta e toca em todo lugar é **copiado** (H.264 e AAC no MP4 e no MOV; VP9, VP8, AV1, Opus e Vorbis no WEBM); o resto é refeito (H.264 e AAC no MP4 e no MOV, VP9 e Opus no WEBM). MP4 ↔ MOV com H.264 e AAC é instantâneo. Tudo copiado usa `copy: { mode: 'forced' }`; o teste confere pacotes iguais aos do original. O WEBM não guarda rotação: vídeo gravado em pé é refeito, já em pé. HEVC (iPhone) para MP4 ou MOV tem a escolha "Compatível" (refaz em H.264, já marcada quando o navegador consegue) ou "Rápido" (copia o HEVC; alguns aparelhos não tocam); os navegadores de teste não leem HEVC, então essa escolha é conferida no teste do painel e no aparelho. Taxa do vídeo refeito: a regra comum de recodificar (abaixo), com a eficiência de cada codec (HEVC e VP9 ≈ 60% do H.264). Som refeito na menor taxa entre 96, 128, 160 e 192 kbit/s que alcança a do original (o AAC do Windows só aceita essas). Ao abrir, o Worker informa, por formato, se o navegador refaz o vídeo e o som (`reencodable`); o que não dá fica desligado com o motivo (ex.: Firefox, sem AAC, não converte para MP4 e MOV quando o som precisa ser refeito).
- Recodificar: MP4 e MOV saem só em H.264 (toca em todo lugar), WEBM em VP9 (ou VP8, AV1), em qualidade alta, mas **nunca acima da taxa do original** proporcional à área do quadro final e convertida pela eficiência de cada codec (`cappedVideoBitrate` em `core/video/sizing.ts`, usada por todas as ferramentas que refazem o vídeo). Sem esse limite, o navegador refazia com qualidade constante alta, e um trecho de 3 s de um vídeo do WhatsApp saía maior que o vídeo inteiro de 6 s; o teste confere com `ja-comprimido.mp4`. O som refeito dentro do vídeo (remover partes, converter) usa a menor taxa entre 96, 128, 160 e 192 kbit/s que alcança a do original (`reencodedAudioBitrate` em `core/video/audio.ts`). H.264 exige lados pares: a área de recorte perde 1 px onde for ímpar (`core/video/crop.ts`), e a tela mostra o tamanho final real. Área mínima de 16 px.
- O que o navegador consegue (decodificar o vídeo, codificar o resultado) é conferido ao abrir; sem isso, refazer fica indisponível com explicação (ex.: HEVC do iPhone em navegador sem o decodificador): no Editar vídeo dá para tirar só o final (copiado), e o recorte fica indisponível.
- Faixas: só a principal de vídeo e a de áudio (com codec conhecido); havendo outras, a tela avisa.
- Criar GIF (`core/video/gif.ts`, `core/image/encode/gif.ts`): trecho de **no máximo 15 segundos** (o GIF é pesado; pedido do usuário), escolhido no player com marcar início e fim ou nos campos de tempo; tamanho de 320, 480 ou 640 px pelo lado maior (só até o do vídeo; vídeo menor fica do tamanho dele) e fluidez de 10 ou 15 quadros por segundo. Só precisa ler o vídeo (`canDecodeVideo`), não refazê-lo. O Worker tira os quadros pelo `CanvasSink` do Mediabunny (já nas medidas finais e em pé) em duas passadas: 16 quadros espalhados montam uma paleta única de 255 cores (corte mediano; cor que não estava nas amostras vai para a mais próxima), e depois cada quadro é gravado na hora, sem guardar o vídeo inteiro. Cada quadro leva só o retângulo que mudou, e dentro dele o que continua igual (ou quase: ruído de compressão) fica transparente, por cima do anterior. Tempos em centésimos (a 15 qps, 7 e 6 alternados, sem desviar do vídeo). Repete sem fim. Medido: fundo parado, 15 s a 640 px e 15 qps, 0,3 MB; câmera andando, 2 MB em 5 s a 480 px e 12 MB em 15 s a 640 px e 15 qps. Sem pontilhado (decisão pelo arquivo mais leve): degradês podem aparecer em faixas, e a tela avisa. O resultado aparece animado com o botão "Pausar animação" (WCAG 2.2.2); com "reduzir movimento" no sistema, já começa parado. O codificador veio do histórico (commit `400bb79`) e ganhou a animação; o leitor independente de GIF dos testes (`src/test/format-readers.ts`) lê quadro a quadro, e o teste do Worker confere também pelo `ImageDecoder` do navegador.
- Texto no Editar vídeo (`core/video/text.ts`, `features/video-tools/edit`): o texto é guardado com o lugar em frações do quadro, o tamanho em fração do lado menor e o tempo em segundos do vídeo original (excluir uma parte leva junto o texto que estava nela). A prévia é um canvas sobre o player desenhado pelas mesmas funções (`layoutText`, `drawText`) que o Worker usa em cada quadro: com texto, `trim` e `join` recebem `look` e o vídeo é sempre refeito (`allowTransformationMetadata: false`, para o quadro chegar em pé como na prévia; o som do corte continua copiado). O Worker carrega do próprio site só as fontes que os textos usam (`FontFace`); onde o Worker não tem fontes (alguns Safari), sai a fonte do sistema. O Worker valida tudo (`sanitizeTexts`: estilo, cor, números, até 20 textos de 120 letras). Desfazer guarda cortes e textos juntos; escrever e mexer no texto aberto é um passo só (no texto novo, o mesmo passo de criar).
- Efeitos no Editar vídeo (`core/video/effects.ts`, `core/video/time-stretch.ts`, `features/video-tools/edit/EffectsPanel.tsx`): filtro (com a força) e ajustes viram **uma matriz de cor só** (3 × 4, em sRGB). A prévia a aplica no `<video>` por um filtro SVG `feColorMatrix` com `color-interpolation-filters="sRGB"` (sem isso, o SVG misturaria em RGB linear e a prévia não seria igual ao arquivo); o Worker, em cada quadro, pela mesma conta (`applyColorMatrix` sobre `getImageData`, canvas com `willReadFrequently`), antes de desenhar os textos, que ficam sem filtro como na prévia. Com cor, o `look` leva `color` e o vídeo é refeito como com texto. **Velocidade** (0,25×, 0,5×, 0,75×, 1×, 1,5×, 2×, 3×, 4×; o Worker aceita só essas): sempre pela tarefa `join` com `speed` (mesmo um trecho só ou o vídeo inteiro), porque o som precisa ser refeito; no Firefox, sem AAC, fica indisponível em MP4 e MOV, com explicação. Os quadros andam `speed` vezes mais depressa, no máximo 60 por segundo (os a mais saem); o som é esticado sem mudar o tom (WSOLA próprio, pedaços de 40 ms com busca de 12 ms pela melhor emenda, em fluxo, com o total exato de amostras), como o player do navegador faz na prévia (`playbackRate`, que mantém o tom). Os tempos guardados (cortes, textos) continuam no tempo do vídeo original; só a duração final é dividida pela velocidade. Desfazer guarda os efeitos com cortes e textos; mexer seguido no mesmo controle deslizante é um passo só.
- Mobile com limites menores e testes em aparelho real. Skills: `architecture-review`, `performance-optimization`, `security-auditor`.

## Skills do projeto (`.claude/skills/`)

Comandos nativos que **complementam** (não duplicar em Skills): `/code-review` (varredura de bugs no diff), `/security-review` (segurança do diff pendente; exige remoto `origin`), `/simplify` (limpeza do código alterado), `/run` e `/verify` (rodar o app e observar o resultado real). O `/debug` nativo depura a sessão do Claude Code, não o código do app; para bugs do projeto use `systematic-debugging`. Fluxo típico de uma funcionalidade: `architecture-review` → `test-driven-development` + `frontend-design` → `accessibility-review` / `security-auditor` / `performance-optimization` conforme o caso → `code-reviewer`.

## Regras permanentes de desenvolvimento
1. Não implementar funcionalidades que não foram solicitadas.
2. Não alterar partes funcionais sem necessidade; preservar o trabalho existente.
3. Não instalar bibliotecas sem justificar (ver política de dependências).
4. Não fazer alterações arquiteturais grandes sem explicar os motivos e esperar aprovação.
5. Não considerar funcionalidade concluída sem testes adequados.
6. Não ignorar erros ou avisos importantes.
7. Não expor informações sensíveis.
8. Não enviar arquivos dos usuários a servidores sem necessidade e autorização explícita.
9. **Não fazer commits nem pushes automaticamente**; só quando o usuário pedir.
10. Explicar alterações importantes de forma clara.
11. Preferir soluções simples, seguras e fáceis de manter.
12. Em revisões, não alterar código sem autorização, exceto quando a tarefa pedir correções explicitamente.
